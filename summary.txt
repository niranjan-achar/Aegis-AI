# An utonomous Self-Evolving Malware Detection System for Real-Time Threat Detection

## Abstract
This project presents an AI-driven, autonomous, and self-evolving malware detecting system for real-time threat detection. The system is designed to detect suspicious Windows binaries using a hybrid pipeline that combines static analysis, image-based deep learning, rule-based intelligence, and explainable AI. It integrates file ingestion, PE feature extraction, byte n-gram modeling, YARA matching, ONNX-based inference, Grad-CAM explainability, telemetry monitoring, risk-driven alerting, and analyst-in-the-loop retraining. The system operates in both full and degraded modes: when optional components such as Redis, MLflow, MongoDB, watchdog, psutil, timm, or torchcam are unavailable, core APIs continue functioning with fallback behavior. The architecture supports practical SOC-style workflows through live telemetry streams, incident grouping, queue-based labeling, and background model updates. Overall, the project demonstrates how AI can be used not only to classify malware but also to adapt continuously through feedback and operational context.

## Keywords
AI Malware Detection, Autonomous Security, Self-Evolving Models, Static Analysis, YARA, ONNX Runtime, Explainable AI, Grad-CAM, Active Learning, Real-Time Threat Detection

## 1. Introduction
Modern malware evolves rapidly through obfuscation, packing, and distribution tactics, making static signature-only solutions insufficient for long-term defense. A practical defense system must detect threats quickly, explain model behavior, and continuously improve from new evidence.

This project is built around three core ideas from the title itself:
1. AI-Driven: use machine learning and deep learning for malware classification.
2. Autonomous: automate ingestion, scanning, telemetry, and alert generation.
3. Self-Evolving: incorporate analyst feedback to retrain and update model artifacts.

## 2. Problem Statement
Most malware analysis workflows are fragmented and require manual tool-switching. Existing setups often miss one or more of the following:
- unified real-time detection pipeline,
- explainable outputs for analyst trust,
- live telemetry and risk correlation,
- feedback-driven continual model adaptation.

## 3. Project Goals and Objectives (Aligned to Title)
### 3.1 AI-Driven Goals
1. Build a hybrid AI pipeline that fuses visual embeddings and handcrafted static features.
2. Improve classification robustness through multi-signal evidence.
3. Provide confidence-oriented outputs for reliable triage.

### 3.2 Autonomous Goals
1. Automate file ingestion, hashing, caching, and scan orchestration.
2. Enable watch-folder auto-scan and live telemetry capture.
3. Generate alerts and incidents automatically from risk rules.

### 3.3 Self-Evolving Goals
1. Queue uncertain samples for analyst review.
2. Trigger retraining using confirmed labels.
3. Validate and deploy updated model artifacts under quality constraints.

### 3.4 Real-Time Threat Detection Goals
1. Stream telemetry and training events through websockets.
2. Keep low-latency inference through ONNX Runtime and cache reuse.
3. Maintain service continuity even when optional dependencies fail.

## 5. System Architecture
The system follows a layered architecture:
- Presentation Layer: React dashboard (Scan, Live, Analytics, Evolution, Queue, Network, Incidents, System, About).
- API and Orchestration Layer: FastAPI routes, websocket channels, scan orchestration.
- Detection Layer: ingestion, binary image conversion, PE extraction, n-gram extraction, YARA, inference, XAI.
- Intelligence Layer: risk engine, alerts, incident grouping.
- Telemetry Layer: watch-folder and network monitoring, event broadcast.
- Data Layer: Redis (optional), JSON fallback store, optional MongoDB, optional MLflow.

## 7. Detailed Methodology and Modules
Each module is described as Inputs, Process, Tools, and Outputs.

### 7.1 Ingestion Module
Inputs:
- Uploaded file
- Optional Redis client

Process:
1. Validate size and content.
2. Compute SHA-256 hash.
3. Check cache by hash.
4. Persist file for scan on cache miss.

Tools:
- fastapi UploadFile, hashlib, redis.asyncio, aiofiles, pathlib

Outputs:
- cache_hit, sha256, file_path, cached_result

### 7.2 Binary Image Conversion Module
Inputs:
- File path, SHA-256

Process:
1. Read bytes.
2. Convert to uint8 array.
3. Reshape into square grayscale matrix.
4. Resize to 224 x 224.
5. Save PNG and base64 output.

Tools:
- NumPy, Pillow, base64

Outputs:
- image_path, image_b64

### 7.3 PE Feature Extraction Module
Inputs:
- File path

Process:
1. Parse PE headers and sections.
2. Compute entropy and section statistics.
3. Extract and compress import-vocabulary signals.
4. Normalize into fixed vector.

Tools:
- pefile, NumPy, hashlib

Outputs:
- feature_vector and PE metadata summary

### 7.4 N-gram Module
Inputs:
- File path

Process:
1. Build byte bigrams.
2. Count frequencies.
3. Apply log scaling.
4. Select indexed bigram features.

Tools:
- NumPy

Outputs:
- ngram_vector

### 7.5 YARA Scanning Module
Inputs:
- File path, rule files

Process:
1. Compile rules safely.
2. Match file and parse strings/offsets/tags.
3. Derive YARA confidence.

Tools:
- yara-python, ThreadPoolExecutor, asyncio

Outputs:
- yara_matches, yara_confidence

### 7.6 Hybrid Inference Module
Inputs:
- Binary image path
- Combined static vector

Process:
1. ONNX image embedding.
2. Embedding plus tabular feature fusion.
3. Classification head probability estimation.
4. Top-3 verdict generation.

Tools:
- onnxruntime, NumPy, joblib, scikit-learn, Pillow

Outputs:
- prediction, confidence, top3, embedding

### 7.7 Explainability Module
Inputs:
- Image path, file path, predicted class index

Process:
1. Compute Grad-CAM activation map.
2. Build overlay heatmap.
3. Map top activations to binary offsets and sections.

Tools:
- PyTorch, timm, torchcam, Pillow, NumPy, pefile

Outputs:
- heatmap artifacts and suspicious offsets

### 7.8 Risk, Alert, and Incident Module
Inputs:
- Scan output, watcher events, network events

Process:
1. Compute threat score.
2. Build severity-based alerts.
3. Persist and broadcast alert events.
4. Group related alerts into incidents.

Tools:
- risk utilities, repository abstraction, event hub

Outputs:
- alerts, incidents, live notifications

### 7.9 Telemetry Module
Inputs:
- File-system and network events

Process:
1. Watch folders for suspicious artifacts.
2. Collect network metadata when enabled.
3. Persist and stream telemetry.

Tools:
- watchdog (optional), psutil (optional), asyncio

Outputs:
- telemetry feed and event-derived alerts

### 7.10 Self-Evolving Retraining Module
Inputs:
- Analyst-confirmed labels
- replay_buffer, fisher_matrix, validation_set

Process:
1. Train with EWC regularization.
2. Validate quality gate.
3. Export updated ONNX and model weights.
4. Version and publish progress.

Tools:
- Celery, PyTorch, timm, ONNX export, MLflow, Redis pub-sub

Outputs:
- retraining decision, updated artifacts, training events

## 8. End-to-End Workflow
### 8.1 Autonomous Scan Workflow
1. Upload or watcher event triggers pipeline.
2. Ingestion validates, hashes, and checks cache.
3. Binary image, PE, n-gram, and YARA branches execute.
4. Hybrid inference computes class and confidence.
5. Explainability module generates visual evidence.
6. Risk engine computes threat score.
7. Scan, alerts, and telemetry are persisted and broadcast.

### 8.2 Self-Evolving Workflow
1. Low-confidence samples enter queue.
2. Analyst confirms ground-truth label.
3. Worker retrains with EWC and replay.
4. Validation gate accepts or rejects deployment.
5. New artifacts become active on successful deployment.

## 12. Real-Time and Reliability Strategy
The system is designed for real-time operation with resilient fallback:
- Redis offline: queue and training channels degrade, core APIs continue.
- MLflow unavailable or incompatible: evolution endpoint returns safe fallback payload.
- psutil unavailable: network and some runtime metrics become limited.
- watchdog unavailable: watch-folder monitoring is reduced.
- timm or torchcam unavailable: explainability is disabled without full service failure.
- motor unavailable: persistence falls back to local JSON store.

## 13. Security and Validation Controls
1. Upload size limits and empty-file checks.
2. SHA-256 based deduplication and traceability.
3. Safe path management using pathlib.
4. Structured API error handling.
5. Separation of heavy tasks into async and worker layers.

## 14. Limitations
1. Primary support currently focused on Windows PE binaries.
2. Full self-evolving loop depends on Redis and worker availability.
